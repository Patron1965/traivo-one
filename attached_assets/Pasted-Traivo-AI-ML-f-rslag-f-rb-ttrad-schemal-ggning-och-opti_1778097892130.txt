Traivo AI/ML-förslag: förbättrad schemaläggning och optimering
1) Nulägesanalys av faktiskt implementation i traivo-one
1.1 Övergripande arkitektur (idag)
Traivo använder idag en hybridmodell:

Node/Express backend orkestrerar jobb, constraints och fallback-logik.

Python FastAPI optimization-service (optimization-service/main.py) löser CVRPTW via OR-Tools.

ALNS-förbättringsfas (optimization-service/alns.py) körs efter OR-Tools för lokala förbättringar.

Geoapify VRP fallback (server/route-optimizer.ts) används när OR-Tools-tjänsten inte är tillgänglig.

Asynkrona jobb hanteras via optimization_jobs-tabellen och optimization-job-runner.ts.

1.2 Det som redan fungerar bra
Robust fallback-kedja

OR-Tools service health check (/health)

fallback till Geoapify / enklare heuristik vid fel

Bra constraint-berikning i backend (server/vrp-constraints.ts)

tidsfönster (hårda + mjuka preferenser)

kompetenskrav

kapacitet

beroenden mellan uppgifter

effektivitetsfaktorer via resourceArticles + resources.efficiencyFactor

Bra avståndsinfrastruktur (server/distance-matrix-service.ts)

OSRM table/route

L1 + L2 cache (distance_cache)

fallback till Geoapify/Haversine

Skalningsmönster finns redan

async threshold (20/30 beroende på väg)

job queue med progress, retries och timeout

1.3 Konkreta gaps/ förbättringsområden (från kod)
A) Prediktioner är heuristiska, inte ML-drivna
I server/ai-planner.ts (generatePredictivePlanning) används:

historiskt snitt

enkel trend (increasing/decreasing/stable)

enkel exponentiell justering

Detta ger låg precision vid:

säsongseffekter

väderpåverkan

team-specifika kapacitetsskillnader

B) Tidsestimat i optimeringen är statiska
estimatedDuration går in som fast duration i både OR-Tools och fallback.

Ingen explicit modell för att prediktera verklig duration per:

objekttyp

executionCode

resurs/team

setup-historik (setup_time_logs)

C) Pre-clustering är geotemporal men ej lärd
DBSCAN/KMeans används (Python + TS), men parametrar är statiska.

Ingen lärd modell för:

optimal cluster sizing

sannolikhet för unassigned stop

churn-risk mellan kluster

D) Ingen online-lärande loop från utfall
Resultat mäts men används inte systematiskt för modelluppdatering.

Exempel på outcomefält finns i schema men inte i en aktiv ML-pipeline:

actualDuration, setupTimeLogs, resourcePositions, outsidePreferredWindow

E) Ingen policy-optimering för dynamisk omplanering
Replanering är i huvudsak regelbaserad (jobbstatus/ny körning), inte policybaserad.

Saknas komponent som beslutar när och hur mycket schema ska förändras vid realtidsstörningar.

2) Målbild: AI-förstärkt optimeringsplattform
Föreslagen målarkitektur:

Prediction Layer (ML)

Optimization Layer (OR-Tools + ALNS + learned priors)

Feedback Layer (MLOps)

kontinuerlig utvärdering

retraining-cykler

Integration i nuvarande flow
Ersätt rå duration i stop payload med predikterad duration_p50.

Lägg duration_p90 som buffert i tidsfönster för riskkänsliga order.

// server/services/mlFeatureAdapter.ts (ny)
export function mapPredictionsToStops(stops, preds) {
  return stops.map(s => {
    const p = preds[s.id];
    return {
      ...s,
      duration: p?.durationP50Sec ?? s.duration,
      metadata: {
        durationP90Sec: p?.durationP90Sec,
        delayRisk: p?.delayRisk,
      },
    };
  });
}

5) Stegvis roadmap
Fas 0 (1–2 veckor): Instrumentering och datagrund
Logga feature snapshots + labels

Standardisera schema för optimization_jobs.result

Lägg till dashboard för baseline-KPI

Leverans: observability + träningsdata redo.

Fas 1 (2–4 veckor): Duration/ETA-modell i produktion (shadow + assist)
Träna första LightGBM-modell

Kör shadow inference parallellt med befintligt flöde

Aktivera gradvis (tenant flag)

Mål: minst 15–25% lägre MAE än dagens statiska estimat.

Fas 2 (3–5 veckor): Forecasting + smart resursallokering
Ersätt enkel trendlogik i generatePredictivePlanning

Introducera demand forecast + capacity warning v2

Modellstyrd cluster-parameterisering

Mål: bättre träffsäkerhet i veckoprognos och färre unassigned.

Fas 3 (4–6 veckor): Dynamisk omplanering (bandit)
Implementera replanningPolicy (contextual bandit)

Koppla till realtidsevents (nya jobb/förseningar)

Mät churn vs SLA-förbättring

Mål: snabbare och stabilare omplanering med kontrollerad schemaförändring.

Fas 4 (6–10 veckor): RL i simulering + kontrollerad rollout
Bygg simuleringsmiljö från historiska Traivo-events

Träna PPO-policy

Human-in-the-loop och gradvis rollout

Mål: förbättrad total reward utan SLA-regression.

6) Risker och mitigering
Datakvalitet: saknade/inkonsekventa labels

Mitigering: datavalidering + confidence-gating

Överanpassning per tenant

Mitigering: global modell + tenant-finetune + fallback

Operativ risk vid auto-replan

Mitigering: max churn guardrails + godkännandeflöde

Latency/Drift

Mitigering: cache, batch inference, drift monitor + rollback

7) Rekommenderad start (konkret nästa sprint)
Implementera ml_feature_snapshots + outcome-loggning i optimization-job-runner.ts.

Träna första duration-modellen på historik (estimatedDuration, actualDuration, setup/objekt/resurs-features).

Lägg till endpoint POST /api/ml/predict/durations och injicera i OR-Tools payload.

Mät KPI före/efter under 2 veckor med A/B per tenant.

Detta ger snabb affärseffekt utan att ersätta befintlig OR-Tools/ALNS-kärna.

8) Sammanfattning
Traivo har redan en stark optimeringskärna (OR-Tools + ALNS + constraints + robust fallback). Den största hävstången nu är att göra inputen intelligent och adaptiv via ML:

bättre duration/ETA,

bättre prognoser,

policybaserad omplanering,

kontinuerlig lärloop från verkliga utfall.

Det föreslagna upplägget minimerar risk genom att bygga ovanpå befintlig arkitektur i traivo-one, stegvis och mätbart.
