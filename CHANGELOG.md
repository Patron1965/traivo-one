## 2026-06 — Enhetligt importprotokoll, fyra nummer (Task #618)
Objektmall-importen (`server/routes/objektmallImportRoutes.ts` + `shared/objektmall-template.ts`, v2) hanterar nu hela livscykeln i **en** fil och **en** körning. Nummerkolumner per rad: `Systemnummer | Interimsnummer | Systemföräldernummer | Interimföräldernummer` + `Objektnamn`; resten är metadata. Per rad klassas en av tre åtgärder: **create** (nytt objekt, matchas på interimsnummer → objectNumber `MALL-<interim>` så re-import inte dubblettar), **update** (matchas i prioritet systemnummer → butiksnummer/objectNumber → unikt butiksnamn), **repoint** (uppdatering vars upplösta förälder skiljer sig från nuvarande `parentId` → flyttar objektet och ärver adress från ny förälder). Föräldern upplöses via interimföräldern (sentinel `NEW:<interim>` för förälder som skapas i samma körning) eller systemföräldernummer. **Krav-regeln stramades:** endast `Objektnamn` + förälder krävs (förälder utelämnas bara för roten/organisationen); allt annat — inklusive adress — är metadata som ärvs nedåt. Uppdateringar är partiella: utelämnade fält och förälder bevaras. Ny **interimslista-flagga** i README-fliken (`OBJEKTMALL_INTERIM_FLAG_MARKER="[INTERIMSLISTA]"`): när satt tolkas alla nummer som interim och system-kolumner ignoreras (`readInterimListFlag`), så en ren nyimport aldrig råkar matcha befintliga systemobjekt. `parseWorkbook` returnerar `interimListFlag`; `validateAll(sheets, tenantId, warnings, interimListFlag)` returnerar per-flik `toCreate/toUpdate/toRepoint` + `actions[]` (rad/åtgärd/namn/detalj) och top-level `interimListFlag`. `commitImport` returnerar `{created, updated, repointed}` (repoint räknas in i `updated` i batch-sammandraget). Alla UPDATE har `tenant_id` i WHERE (defense-in-depth). Frontend (`client/src/pages/admin/ObjektmallImportPage.tsx`) visar interimslista-banner, per-flik repoint-badge, per-rad åtgärdslista och repoint-kolumn i commit-resultatet.

## 2026-05 — Auto-checkpoint massradering (Task #532)
Replits auto-checkpoint commit:ar exakt disk-state vid loop-avslut utan integritetskontroll — om en agent-session råkar radera/flytta en mapp och inte slutför, commit:as raderingen som "Saved progress at the end of the loop" utan varning. Referens-incident: 351 filer i `client/` försvann (`bd3e73d`), upptäcktes 24h senare via preview-`ENOENT`, återställdes via `git show <parent>:<path>` per fil (sandbox blockerar `git checkout`). Tripwire: `npx tsx scripts/check-mass-deletion.ts --commits 50 --threshold 50` (kör veckovis + obligatoriskt före varje `git push github main`, även fast-forward). Tripwiren räknar endast äkta `D`-status (renames `R*` och copies `C*` exkluderas, så legitima omflyttningar triggar inte falskt larm). Full återställnings-procedur: `docs/disaster-recovery.md` §Scenario D + §10 (GitHub-mirror-rutin). Post-mortem: `docs/incidents/2026-05-21-client-deletion.md`.

Audit-rad skrivs till `feature_audit_log` med `changedBy="system"`. Full doc: `docs/kinab-pilot-modules.md`.

## 2026-05 — Disaster Recovery runbook (Task #525)
Komplett DR-runbook i `docs/disaster-recovery.md` täcker: vad Replit backupar (DB: 7d PITR via Neon, Object Storage: multi-region GCS-replikerat — ingen separat snapshot, riskaccepterat), RPO 24h/RTO 4h-mål för pilot, tre scenarion (DB borta / app-deploy borta / Object Storage borta) med konkreta steg, kontakt-/eskaleringskedja, Replit Checkpoints-scope (täcker dev-DB + kod, **inte** prod), och kvartals-checklista. **Replit Object Storage backupas inte separat** — risken är dokumenterat accepterad eftersom mobil-appen håller fotot lokalt i minst 30d efter upload-bekräftelse (de facto secondary copy). Replit PITR-restore via konsolen mot staging-DB pending före pilot go-live (se runbook §7).

## 2026-05 — Degraded mode + fallback-banner (Task #524)
`server/services/external-service-health.ts` exponerar `getIntegrationsHealth(tenantId?)` som kontrollerar 7 integrationer (Geoapify, OpenAI, Twilio, Resend, Object Storage, Fortnox per-tenant, OSRM). Varje check är "billig" (env-/config-baserad, ingen live-API-anrop) och cachas 60s per `(id, tenantId)`-nyckel. `GET /api/system/integrations/health` returnerar `{overall:"ok"|"degraded", integrations:[...]}`. Frontend-komponent `client/src/components/layout/DegradedModeBanner.tsx` infogad i `AuthenticatedApp` ovanför `TopNav`, pollar var 60s, kan dismissas i 30 min (`localStorage`). Severity-modellen: `critical` = banner alltid, `important` = banner när degraderad, `optional` = endast synlig i detalj-vyn (gäller OSRM). Inga nya try/catch behövs — befintliga skyddsräcken används: `routing.ts` returnerar null när nyckel saknas (Haversine-fallback), `FortnoxClient.isConnected()` styr export-gate, `isTwilioConfigured()` styr SMS, `unified-notifications.ts` failar mjukt per kanal. Fullt protokoll: `docs/degraded-mode-runbook.md`.

## 2026-05 — Observability: loggar, healthz, Sentry (Task #523)
Strukturerad loggning via `pino` (`server/logger.ts`) med redact för auth-headers + token-/secret-/password-fält. Per request tilldelas en `requestId` av `server/middleware/request-id.ts` (UUID, eller inkommande `x-request-id` om ≤128 tecken), returneras som header och loggas via `req.log`. Felmiddleware loggar `{status, err, route, method, tenantId}` och svarar `{error, requestId}`. `GET /healthz` (`server/routes/healthRoutes.ts`) returnerar 200/`{status:"ok"}` när DB-`SELECT 1`, `OPTIMIZATION_SERVICE_URL/health` (2s timeout) och `GEOAPIFY_API_KEY` är ok — annars 503. Resultatet cachas 5s in-memory. `/health` (utan z) finns kvar som trivial liveness-probe; använd `/healthz` för fullstack-readiness i prod. Frontend-Sentry initieras i `client/src/main.tsx` via `client/src/lib/sentry.ts` när `VITE_SENTRY_DSN` är satt (build-time, kräver omkompilering), `tracesSampleRate=0`. `ErrorBoundary.componentDidCatch` skickar fel utom stale-asset/chunk-load-fel. `setSentryTenant(tenantId)` taggar events. `LOG_LEVEL` styr nivå (default `info` prod, `debug` dev, `warn` test).

## 2026-05 — Audit-logg retention (Task #511)
`auditCleanupScheduler` (`server/services/audit-cleanup-scheduler.ts`) körs dagligen (default 24h, första körning +15 min) och rensar `audit_logs` i två kategorier: login-rader (`action LIKE 'auth.login%'`, default 365 dagar) och övriga rader (default 730 dagar). Konfigurera med `AUDIT_LOG_LOGIN_RETENTION_DAYS` resp `AUDIT_LOG_RETENTION_DAYS`. Slå av med `AUDIT_LOG_CLEANUP_ENABLED=false`. Justera intervall via `AUDIT_LOG_CLEANUP_INTERVAL_MS` / `AUDIT_LOG_CLEANUP_INITIAL_DELAY_MS`. Manuell trigger: `POST /api/admin/audit-logs/cleanup` (admin/owner-session **eller** `x-cleanup-token: $AUDIT_LOG_CLEANUP_TOKEN` för extern cron). Två separata `DELETE … WHERE created_at < NOW() - (N || ' days')::interval`-satser; returnerar `{ loginDeleted, otherDeleted, loginDays, otherDays }`. Retention är dimensionerad så att de partial-indexen från Task #510 hålls små.

## 2026-05 — Platform-logins indexering (Task #510)
`GET /api/platform/logins` filtrerar `audit_logs` på `action IN ('auth.login','auth.login.failed')` + `metadata->>'method'`/`metadata->>'email'` samt fri-text `q` (ILIKE mot email+ip). Tre partial-index täcker hot-path (alla `WHERE action LIKE 'auth.login%'`): `idx_audit_logs_login_created` btree `(action, created_at DESC)`, `idx_audit_logs_login_method` btree `((metadata->>'method'))`, `idx_audit_logs_login_email` btree `((metadata->>'email'))`. **Begränsning:** btree accelererar inte `ILIKE '%term%'` (q-fri-text-filter) — trigram-GIN togs medvetet inte med pga deploy-historiken (`migrations/0033_drop_raw_trgm_indexes.sql`). Om q-sök blir hot-path, lägg till trigram bakom separat migration som kör `CREATE EXTENSION IF NOT EXISTS pg_trgm`.

## 2026-05 — Magic-link-inloggning (Task #515)
Nya användare bjuds in via UI (`Tenant Config → Inbjudningar` eller `Användarhantering → Inbjudningar`, owner/admin) eller direkt via `POST /api/admin/invitations { email, role }` / `POST /api/invitations { email, role }`. Båda backend-endpoints går genom magic-link-flödet (`server/routes/kpiRoutes.ts:sendInvitationEmail` → `issueMagicLink({ invitationId, baseUrl, req })`). `POST /api/invitations` och `/api/invitations/:id/resend` sätter `expiresAt = now + 7d`. Backend skapar invitation-rad (`status=pending`) och skickar magic-link via Resend (`server/replit_integrations/auth/magicLinkAuth.ts`). Mottagaren klickar → `GET /api/auth/magic-link/consume?token=…` → SHA-256-token-hash jämförs mot `magic_link_tokens`, race-safe markeras `consumedAt`, users-rad upsertas, `processInvitations` + `ensureDefaultTenantAssignment` körs, `req.logIn` skapar session `{claims:{sub,email,exp}, expires_at, auth_method:"magic_link", refresh_token:null}`. TTL 15 min, engångsbruk. Sessionen lever på `expires_at`; saknar refresh-token → ny länk kan behövas efter ~1 vecka. Login-sidan (`/login`) har magic-link-formulär ovanpå "Logga in med Replit"; fel exponeras via `?magic_error=…`. `POST /api/auth/magic-link/request` returnerar alltid `204` (ingen email-enumeration) och är rate-limitad via `magicLinkLimiter`. Kräver `RESEND_API_KEY`.

## 2026-05 — Tile-proxy skydd (Task #481)
`GET /api/system/map-tiles/:z/:x/:y` är skyddad i tre lager: (1) `mapTileLimiter` per-IP 600 anrop/min (`MAP_TILE_RATE_LIMIT_PER_MIN`); (2) Origin/Referer-kontroll i prod mot allowlist (`MAP_TILE_ALLOWED_HOSTS` + `REPLIT_DOMAINS`, sub-domäner matchar) — `Host`-headern används medvetet inte (spoofbar). Om ingen allowlist konfigurerad faller skyddet "open" (rate-limit ensam), så sätt `MAP_TILE_ALLOWED_HOSTS` i prod; (3) timvis volymräknare som loggar `[map-tiles-proxy] HÖG VOLYM` första gången tröskeln passeras (`MAP_TILE_HOURLY_ALERT_THRESHOLD`, default 20 000/h). Dev/test bypassar rate-limit (NODE_ENV=test) och Origin-checken (NODE_ENV !== production).

## 2026-05 — VRP-prestanda för stora indata (Task #490)
DBSCAN-pre-clustering använder grid-baserad spatial index (`server/dbscan-clustering.ts`) i stället för O(N²)-distansmatris — kandidat-radien är `epsilonKm/(1-temporalWeight)` (säker eftersom temporal-distans alltid ≥0). 1000 stopp körs på <500 ms (uppmätt 81 ms; matrix-versionen 103 ms). Cluster-VRP-anrop går parallellt via `p-limit` (`server/route-optimizer.ts`, ~rad 611) — 4 kluster med ~1500 ms Geoapify-latency går från ~6 s seriellt till ~1.5 s. Backout: `DBSCAN_USE_KDTREE=false`, `VRP_PARALLEL_CLUSTERS=false`. Concurrency: `VRP_PARALLEL_CONCURRENCY` (default 4). L2-cache-läsningar i `getBatchDistances` (`server/distance-matrix-service.ts`) batchas via `WHERE id IN (...)` (chunkad 1000) i stället för per-pair SELECT. Benchmark: `npx tsx scripts/benchmark-route-optimizer.ts` → `docs/benchmark-route-optimizer.json`. Regressionstester: `tests/api/dbscan-clustering.test.ts`, `tests/api/route-optimizer-vrp.test.ts`.
